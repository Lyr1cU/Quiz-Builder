# Quiz Builder — план развития

Подробный пофазовый план доработок поверх текущего стека: **Express + Prisma + PostgreSQL** / **Next.js App Router**. Сейчас нет auth, play-режима, AI и PDF; квизы полностью публичны и отдаются вместе с правильными ответами.

---

## Цели (что получим в итоге)

1. **Авторизация** — JWT; email+password (OAuth не планируем); гости проходят, не создают.
2. **Видимость тестов** — `public` (видят все) и `private` (только создатель + доступ по пригласительной ссылке).
3. **Типы выбора** — `SINGLE` (один ответ, radio) и `MULTIPLE` (несколько, checkbox) вместо единого CHECKBOX.
4. **Игровой режим** — прохождение теста с мгновенной обратной связью (верно / неверно; при ошибке — ответ пользователя и правильный).
5. **AI-проверка INPUT** — семантическое сравнение ответа пользователя с эталоном (`inputAnswer`).
6. **PDF для школ** — два файла: лист с вопросами и лист с ответами.

---

## Рекомендуемый порядок работ

Порядок выбран так, чтобы каждая фаза давала рабочий инкремент и не ломала следующие.

| # | Фаза | Зачем именно сейчас |
|---|------|---------------------|
| 0 | Фундамент схемы и контрактов | Общие модели (User, visibility, invite) до UI-фич |
| 1 | Auth | Без владельца нельзя private / invite / безопасный play |
| 2 | Ownership + Public/Private + Invite | Закрывает утечку ответов и доступ |
| 3 | Play mode (локальная проверка BOOLEAN / SINGLE / MULTIPLE) | Базовый UX прохождения без AI |
| 4 | AI-проверка INPUT | Навешивается на уже готовый submit/play API |
| 5 | PDF export | Не зависит от AI; удобно после стабильной модели квиза |
| 6 | Полировка (edit, UX, тесты, docs) | Когда ядро стабильно |

**Почему не AI и PDF раньше auth/play:** без владельца и без скрытия ответов в API «private» и «школьный PDF» бессмысленны; AI нужен только в момент проверки INPUT при прохождении.

## Фаза 0 — Фундамент данных и API-контракты

### Задачи

- Расширить Prisma-схему:
  - `User` (id, email, passwordHash / provider ids, name, createdAt)
  - `Quiz`: `ownerId`, `visibility` (`PUBLIC` | `PRIVATE`), `inviteToken` (nullable/unique)
  - `QuestionType`: вместо одного `CHECKBOX` — **`SINGLE`** (один правильный) и **`MULTIPLE`** (несколько правильных); оставить `BOOLEAN`, `INPUT`
  - Опционально позже: `QuizAttempt`, `AttemptAnswer` — если нужна история прохождений
- Миграция существующих `CHECKBOX`: если в options ровно один `isCorrect: true` → `SINGLE`, иначе → `MULTIPLE`
- Зафиксировать правило: **эндпоинты прохождения не отдают правильные ответы до проверки** (или отдают только verdict после submit).
- Миграции Prisma вместо «только db push» для продакшена (по возможности).
- Обновить seed: тестовый пользователь + public/private квизы + примеры SINGLE и MULTIPLE.

### Критерий готовности

Схема согласована, миграция применяется локально, типы фронта/бэка обновлены под новые поля (даже если UI ещё минимальный).

## Фаза 1 — Авторизация

### Backend

- Регистрация / логин (email + password **и** OAuth).
- **JWT access token** как основной механизм auth (безопасность API):
  - после login/register/OAuth сервер выдаёт JWT (`sub` = userId, email, exp);
  - клиент шлёт `Authorization: Bearer <token>` на защищённые эндпоинты;
  - секрет `JWT_SECRET`, разумный TTL, валидация подписи и expiry в middleware;
  - logout на клиенте = удаление токена (при необходимости позже — refresh token / blacklist).
- Middleware `requireAuth` / `optionalAuth` (читает Bearer JWT).
- Эндпоинты: `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, OAuth callback.
- Привязка `POST /quizzes` к `ownerId = currentUser`.
- `DELETE /quizzes/:id` — только владелец.

### Frontend

- Страницы `/login`, `/register`.
- Хранение JWT (предпочтительно memory + `localStorage` / sessionStorage — зафиксировать при реализации; не класть в URL).
- API-клиент автоматически добавляет `Authorization: Bearer …`.
- Защита `/create` и действий удаления.
- Nav: вход / выход / имя пользователя.

### Критерий готовности

Без валидного JWT нельзя создавать/удалять тесты; с JWT — можно; гости без токена проходят public/invite.

## Фаза 2 — Public / Private + пригласительные ссылки

### Модель доступа

| Visibility | Список | Открыть по id | Play | Редактирование / удаление |
|------------|--------|---------------|------|---------------------------|
| `PUBLIC` | В общем каталоге (гости и юзеры) | Все | Да (в т.ч. гости) | Только владелец |
| `PRIVATE` | Только у владельца | Владелец **или** валидный invite | То же (гости по invite — да) | Только владелец |

### Backend

- Поле `visibility` + `inviteToken` (генерация при создании private или по кнопке «создать ссылку»).
- `GET /quizzes` — public для всех + свои private для владельца.
- `GET /quizzes/:id` — проверка прав; для play-версии — **без** правильных ответов.
- `GET /quizzes/invite/:token` (или `?invite=`) — выдать квиз для прохождения (без answers).
- Ротация / отзыв invite-токена (желательно).

### Frontend

- В форме создания: переключатель Public / Private.
- На детальной странице владельца: копирование invite-ссылки.
- Список: бейдж видимости; вкладки «Все публичные» / «Мои».
- Роут вида `/play/invite/[token]` или `/quizzes/invite/[token]`.

### Критерий готовности

Чужой private-квиз по обычному id недоступен; по invite — доступен для прохождения; ответы не утекают в list/detail для чужих.

### Важно (безопасность)

Сейчас `GET /quizzes/:id` отдаёт `inputAnswer`, `booleanAnswer`, `isCorrect`. Это нужно **разделить**:

- `GET` для владельца / редактора — полные данные.
- `GET` для игрока — только текст вопросов и варианты **без** флагов правильности.

## Фаза 3 — Игровой режим (базовый)

### UX (v1, как в запросе)

1. Пользователь открывает тест → режим Play.
2. Отвечает на вопросы (по одному или все сразу — уточнить).
3. После ответа / после submit по вопросу:
   - **Верно** — сообщение «Правильно».
   - **Неверно** — «Неправильно», показать ответ пользователя и правильный эталон.
4. В конце — краткий итог (score / список ошибок) — желательно в v1.

### Backend

- `POST /quizzes/:id/attempts` или `POST /quizzes/:id/check`:
  - тело: ответы пользователя;
  - сервер сверяет BOOLEAN / SINGLE / MULTIPLE локально;
  - INPUT: пока точное/нормализованное сравнение **или** заглушка до фазы 4;
  - ответ: per-question verdict + correctAnswer (только после проверки).
- Не отдавать correct answers в GET play-payload.

### Frontend

- Роут `/quizzes/[id]/play` (и invite-вариант).
- UI вопросов без подсветки правильных опций до проверки.
- Экран результата по вопросу / итоговый экран.

### Критерий готовности

Можно пройти public-тест end-to-end с мгновенной обратной связью для BOOLEAN, SINGLE и MULTIPLE; INPUT хотя бы с string-compare.

## Фаза 4 — AI-проверка INPUT (семантика)

### Суть

Для типа `INPUT`: эталон = `inputAnswer` (в UI — «Expected answer»). ИИ решает, совпадают ли **по смыслу** ответ пользователя и эталон, и возвращает вердикт (верно / неверно + опционально краткое обоснование).

### Backend

- Сервис `gradeInputAnswer({ expected, actual, questionText? })`.
- Провайдер: OpenAI / Anthropic / Vercel AI Gateway — по выбору (см. вопросы).
- Строгий JSON-ответ модели, например: `{ "isCorrect": boolean, "confidence": number, "rationale": string }`.
- Таймауты, ретраи, fallback на нормализованный string-compare при ошибке API.
- Лимиты: rate limit на пользователя / attempt (стоимость).
- Env: `AI_API_KEY`, модель, опционально `AI_GRADING_ENABLED`.

### Интеграция в play

- В check/attempt pipeline: BOOLEAN / SINGLE / MULTIPLE — локально; INPUT — AI (или hybrid: сначала exact match → если нет, AI).
- Логировать usage (хотя бы в dev) для контроля стоимости.

### Frontend

- Для INPUT в результате: вердикт + (опционально) короткое «почему» от ИИ.
- Индикатор «проверяем…» на время запроса.

### Критерий готовности

Синонимы / перефраз засчитываются; явный бред — нет; при падении AI есть предсказуемый fallback.

### Риски

- Стоимость и latency.
- Нестабильность вердиктов → нужны температура низкая, чёткий prompt, возможно двойной порог confidence.
- Язык ответов (RU/EN) — указать в prompt.

## Фаза 5 — PDF для школ (вопросы + ответы)

### Продукт

Из готового теста владелец (или авторизованный пользователь с доступом) скачивает:

1. **Worksheet** — название, вопросы, поля/варианты для ответа; **без** правильных ответов.
2. **Answer key** — те же вопросы + правильные ответы (для учителя).

### Реализация (варианты)

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| Server-side (PDFKit / Puppeteer) | Единый вид, контроль доступа | Тяжелее деплой (особенно Puppeteer) |
| Client-side (jsPDF / react-pdf) | Проще хостинг | Легче обойти «скрытие» если данные уже в браузере |

**Рекомендация:** генерация на **backend** по запросу владельца (`GET /quizzes/:id/export/pdf?variant=questions|answers`), чтобы answer key не утекал игрокам.

### Frontend

- Кнопки на странице владельца: «Скачать тест (PDF)», «Скачать ответы (PDF)».
- Простая типографика, A4, крупные шрифты, нумерация вопросов — «школьный» вид.

### Критерий готовности

Два PDF скачиваются; в worksheet нет эталонов; в answer key они есть; private-квиз экспортирует только владелец.

## Черновик изменений схемы (ориентир)

```prisma
enum QuizVisibility {
  PUBLIC
  PRIVATE
}

enum QuestionType {
  BOOLEAN
  INPUT
  SINGLE    // один правильный ответ — radio (кружок)
  MULTIPLE  // несколько правильных — checkbox (квадратик)
  // CHECKBOX удаляется; миграция: 1 correct → SINGLE, иначе → MULTIPLE
}

model User {
  id           String   @id @default(cuid())
  email        String   @unique
  passwordHash String?
  name         String?
  createdAt    DateTime @default(now())
  quizzes      Quiz[]
}

model Quiz {
  id          String         @id @default(cuid())
  title       String
  description String?
  createdAt   DateTime       @default(now())
  ownerId     String
  owner       User           @relation(fields: [ownerId], references: [id])
  visibility  QuizVisibility @default(PUBLIC)
  inviteToken String?        @unique
  questions   Question[]
}

// Question.options для SINGLE и MULTIPLE: [{ label, isCorrect }]
// SINGLE: ровно один isCorrect === true (валидация Zod)
// MULTIPLE: ≥1 isCorrect === true
// inputAnswer остаётся эталоном для INPUT (AI + PDF answer key)
```

Миграция существующих строк: seed/типовые пользователи + `ownerId`; `CHECKBOX` → `SINGLE`/`MULTIPLE` по числу правильных опций.

## Принятые решения

| Тема | Решение |
|------|---------|
| Auth | **Email + password** (без OAuth). Саморегистрация открыта. |
| Auth token | **JWT** (`Authorization: Bearer <token>`). Middleware проверяет подпись и expiry. `JWT_SECRET` в env. Гостевые play-эндпоинты без токена. |
| Гости | **Да.** Гость проходит public-тесты и тесты по invite-ссылке; **не** создаёт тесты и не управляет ими. |
| Default visibility | **PUBLIC** по умолчанию. |
| Invite (v1 interim) | Бессрочный токен; владелец может **перевыпустить/отозвать**. TTL и лимиты — позже, если понадобится. |
| Каталог | Общий список **public**; свои (public + private) — у владельца. |
| Типы вопросов (выбор) | Вместо одного `CHECKBOX` — два типа: **`SINGLE`** (ровно один правильный; UI — **radio / кружок**) и **`MULTIPLE`** (несколько правильных; UI — **checkbox / квадратик**). Валидация: SINGLE → ровно 1 `isCorrect`; MULTIPLE → ≥1. Проверка в play: полное совпадение выбранного набора с эталоном (для SINGLE — одна опция). |
| Play UX (v1) | Режим **тренировка**: проверка **после каждого вопроса**; при ошибке показать ответ ученика и правильный. Другие режимы — позже. |
| Попытки в БД | **Да** (фаза 6): сохраняем только для **залогиненных** после practice; историю видит **только сам прошедший**, не создатель. Гости — без истории. |
| Экзамен-режим | **Не делаем** в v1 (только тренировка). |
| AI provider | **Groq** (бесплатный tier). Вердикт только `isCorrect`; **без** rationale для ученика. |
| AI язык | Пока эталоны/ответы ориентир **EN** (prompt под English). |
| AI fallback | При ошибке Groq — нормализованный string-compare (exact / trim / casefold). |
| PDF layout | Два отдельных файла. Worksheet: пустые поля **Name / Date** сверху, место под **Grade** снизу. Answer key — с эталонами. |
| PDF доступ | **Public** — скачать может кто угодно; **Private** — только создатель. |
| Роли | Все зарегистрированные пользователи **равноправны** (создатели). Отдельных ролей ученик/учитель нет. |
| Поле `inputAnswer` | **Не переименовывать**; в плане/AI это и есть expected answer. |
| Миграция старых квизов | В seed завести **типовых пользователей** и привязать существующие квизы к ним. В репозитории seed сейчас создаёт **1** квиз (`JavaScript Basics`); если в локальной БД есть ещё данные — при миграции тоже раздать владельцам. `CHECKBOX` → `SINGLE`/`MULTIPLE`. |
| Режим работы | **Продукт:** план → агент пишет код по шагам → автор сверяет, что работает. Режим «пазл/пиши сам» снят. Параллельно отдельный трек теории собесов — см. [`LEARNING.md`](LEARNING.md). |

### Как это меняет фазы (кратко)

- **Фаза 0:** enum `SINGLE` + `MULTIPLE`; UI/валидация radio vs checkbox; миграция со старого `CHECKBOX`.
- **Фаза 1:** JWT Bearer после login/register/OAuth; `requireAuth` на create/delete; guest play без JWT.
- **Фаза 3:** per-question check; SINGLE/MULTIPLE — полное совпадение выбора с эталоном.

## Миграция хостинга: уход с Render

**Проблема сейчас:** на Render free web service засыпает без трафика; первый запрос после сна — долгий cold start (плохо для демо и школы).

**Желание:** переехать на другой хостинг, **скорее обратно на Vercel** (или сопоставимый вариант без sleep на бесплатном/дешёвом тарифе).

### БД и переезд на Vercel (без лишней боли)

Prisma ходит в Postgres только по `DATABASE_URL` — **хостинг приложения ≠ провайдер БД**.

| Сценарий | Сложность | Что делать |
|----------|-----------|------------|
| БД уже **внешняя** (Neon, Supabase, Railway Postgres, свой VPS) и остаётся | Низкая | Меняем только деплой UI/API на Vercel, те же env (`DATABASE_URL`). Данные не трогаем. |
| БД на **Render Postgres** (или другом хосте, который уйдёт вместе с Render) | Средняя | Один раз: `pg_dump` → новый Postgres (Neon/Supabase/…) → `pg_restore` / Prisma migrate → обновить `DATABASE_URL`. |
| Локальная / embedded Postgres | Только для dev | В проде всё равно нужен managed Postgres. |

**Важно для Vercel (serverless):** не «обязателен Neon», но удобен **пулер соединений** (Neon pooler, Supabase pooler, Prisma Accelerate) — у serverless много коротких коннектов, прямой `postgresql://` без pooler иногда упирается в лимит connections. Для always-on API (вариант B) обычный `DATABASE_URL` часто ок как есть.

**Факт по проекту:** Postgres уже на **Neon**; на Render крутятся только API и frontend. Переезд на Vercel = смена хостинга приложений + те же `DATABASE_URL` / pooler-URL от Neon. **БД переносить не нужно** — Neon этому не мешает.

### Варианты (ориентир)

| Вариант | Frontend | Backend (Express) | Postgres | Плюсы / минусы |
|---------|----------|-------------------|----------|----------------|
| **A. Vercel + serverless API** | Next на Vercel | Express → Route Handlers / отдельный Node serverless, либо постепенно в Next API | Neon / Supabase / Vercel Postgres | Один деплой, нет sleep на Hobby; Express целиком «как есть» не всегда удобен — нужна адаптация |
| **B. Vercel (UI) + отдельный always-on API** | Next на Vercel | Railway / Fly.io / Render paid | тот же managed Postgres | Меньше переписывания Express; платный always-on за API |
| **C. Всё на Vercel через монолит Next** | App Router + Server Actions / Route Handlers | Prisma в тех же функциях | Neon / Supabase | Максимально «vercel-native»; больше рефакторинга бэка |

**Рекомендация в плане:** закладывать фичи так, чтобы бэк оставался тонким HTTP API (JWT Bearer, CORS) — это облегчит и **A**, и **B**. Саму миграцию хостинга делать **после ядра (фазы 0–5)** или параллельно с фазой 6, чтобы не смешивать продуктовые фичи с переносом инфраструктуры.
